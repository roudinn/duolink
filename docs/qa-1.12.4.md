# DuoLink 1.12.4 — проверка задержки и лобби

Дата: 12 ноября 2026. База: `v1.12.3`, `b37f982`.
Windows 11 Pro for Workstations, build 26300; RTX 2060, драйвер 32.0.16.1714;
экран 1920×1080, 144 Гц. Rust/Cargo 1.99.1, x86_64-pc-windows-msvc,
MSVC Build Tools 18, Windows SDK, bundled CMake. Второго ПК нет.

## Что исправлено

- В v1.12.3 каждый поздний гость мог независимо запросить до 15 Мбит/с.
  На общем слабом аплоаде это создаёт очередь и потери для уже играющих.
  Теперь хост резервирует полосу при Ready, учитывает фактически выбранный
  гостем битрейт и освобождает резерв при его выходе. Общий бюджет — 60%
  измеренной скорости; 35% остаётся ограничением первого автоматического потока.
- Незавершённые правки из исходной рабочей копии учитывали резерв, но округляли
  исчерпанный бюджет вверх до 500 кбит/с. Воспроизведено падающим тестом:
  capacity=12000, reserved=7200, audio=200 давали 500 вместо отказа.
  Теперь при нехватке полосы новый поток отклоняется. Ручной битрейт сохраняется
  точно и также проверяется на соответствие свободному бюджету.
- Резерв включает транспортные расходы, дополнительный звук DuoLink и запас
  для звука Sunshine на низких битрейтах. Sunshine сам учитывает FEC в запросе
  Moonlight: повторно прибавлять весь FEC к запросу не нужно.
- Удаление гостя из лобби теперь закрывает его QUIC-туннель независимо от
  реакции клиента. Финальному сообщению даётся 100 мс. Остальные гости остаются.
  Это прекращает поступление ввода; время освобождения устройства при аварии
  дополнительно зависит от обработки отключения/таймаута Sunshine.
- После опустевшего лобби нагрузочный замер снова разрешается, старая оценка
  канала сбрасывается. Во время активной трансляции пробы по-прежнему запрещены.
- Адреса CGNAT 100.64.0.0/10 учитываются как интернет, а не как локальная сеть.

Разрешение, FPS, кодеки и режимы контроллеров сохранены. Низкая задержка
достигается ограничением нагрузки; новая версия не обещает меньшую задержку
свободного канала и не меняет настройки энкодера ради такого обещания.

## Локальное сравнение: реальные Sunshine/Moonlight и виртуальный геймпад

Одинаковые параметры: 1080p, 144 FPS, запрос 30 Мбит/с, HEVC/NVENC P1,
один ПК, Moonlight в окне. 80 событий кнопки в каждом прогоне, первые 8
прогревочных событий исключены. Непрерывный цветовой маркер наблюдался ещё
12 секунд, первая секунда исключена. Квантили — ближайший индекс в
отсортированных наблюдениях. «Длинная пауза» — интервал более 50 мс.

| Метрика, мс | v1.12.3 медиана / p95 / p99 | Новая версия медиана / p95 / p99 |
|---|---:|---:|
| Гостевой виртуальный DS4 → XInput хоста | 1,671 / 3,245 / 3,423 | 1,634 / 3,029 / 3,170 |
| Кнопка → пиксель в окне гостя | 18,299 / 22,810 / 23,995 | 17,083 / 23,247 / 24,044 |
| Обновление маркера хоста → пиксель гостя | 16,530 / 21,168 / 22,148 | 15,620 / 19,205 / 20,501 |
| Между наблюдаемыми кадрами | 7,111 / 14,483 / 16,122 | 7,060 / 14,253 / 15,107 |
| Паузы >50 / >100 мс | 0 / 0 (1356 интервалов) | 0 / 0 (1404 интервала) |

Разница медиан не доказывает устойчивого ускорения: p95/p99 полного пути
практически не улучшились, выборка кнопок небольшая. Прежние 15,9 мс не
использованы как новый результат. Состояние Windows и фаза кадра влияют на тест.

Это **локальная программная проверка**, а не игра на двух ПК и не измерение
фотодиодом. В цепочке реально участвуют ввод Moonlight, QUIC, XInput Sunshine,
отрисовка GDI, захват, NVENC, декодер Moonlight и оконный вывод. Физическая
кнопка и сканирование панели не измеряются. Захват, кодирование, декодирование
и композиция отдельно не инструментированы; измерен их совокупный участок.
Сам GDI-маркер обновлялся примерно 129 раз/с при запросе потока 144 FPS.

## Ограниченный общий аплоад

Реальные QUIC-соединения проходят через локальный UDP-ограничитель:
12 Мбит/с на всех гостей, очередь 250 мс, задержка 5 мс. Кадры синтетические,
запрос 144 FPS, без видеокодека и восстановления FEC. Первому гостю назначены
4,2 Мбит/с; через секунду приходят ещё два. Сравниваются политики выделения
полосы при одинаковой модели трафика, а не два запущенных релизных EXE.
Отдельный прогон добавляет детерминированную потерю каждого сотого пакета.

Итоговый лог: [network.txt](qa-1.12.4/network.txt).

| Первый, уже играющий гость | До: медиана / p95 / p99, мс | После: медиана / p95 / p99, мс | Паузы >50 мс до → после |
|---|---:|---:|---:|
| Доставка полного синтетического кадра, без случайных потерь | 255,842 / 256,744 / 257,094 | 9,518 / 10,366 / 10,651 | 13 → 0 |
| То же, дополнительно 1% потерь | 255,815 / 256,814 / 257,161 | 9,477 / 10,375 / 10,708 | 14 → 0 |

В измерительном окне около 4 секунд без случайных потерь полностью доставлено
277 → 577 кадров первого гостя; незавершённых 296 → 0. С потерями: 272 → 544
полных и 305 → 33 незавершённых. Для таймеров эмулированного канала включён
период 1 мс; это настройка теста, не изменение пересылки пакетов приложения.
Нулевое число пауз у полностью голодающего позднего потока **не** означает
плавность: в логе до исправления у него нет ни одного полного кадра.

Новая политика допускает второго гостя с 0,5 Мбит/с и отклоняет третьего.
Расчётный расход двух потоков вместе со звуком/накладными расходами — 6,982
Мбит/с при бюджете 7,2 Мбит/с. **Картинка второго гостя существенно хуже**,
особенно в движении; его разрешение и FPS сохраняются. Уже играющий гость
не перезапускается. Освободившаяся полоса доступна следующему подключению,
но битрейт уже открытого потока автоматически не увеличивается.

## Функциональные проверки

- `cargo test --release --locked`: 28 passed, 10 ignored по умолчанию;
  необходимые интеграционные проверки запущены отдельно.
- `cargo build --release --locked`: Windows x64 release, версия 1.12.4.
- `live_loopback`: реальные захват, кодирование, приём, декодирование;
  два гостя, выход первого без остановки второго, завершение хоста,
  повторное лобби, отклонение неверного кода и запроса. 1080p/144 FPS;
  проверяется сохранение заданного режима и частоты монитора хоста.
- `seven_guests_keep_independent_tunnels`: семь соединений, отдельные маршруты
  звука, остановка проб, принудительное удаление одного клиента без остановки
  второго, повторное подключение и возобновление проб.
- `live_audio_without_voice_chat`: одновременно Opus и PCM, по 400 пакетов
  за 2 секунды; удалённый получатель больше не получает звук.
- `process_loopback_activates`: Windows process loopback запускается.
  Unit-тест Opus проверяет 5-мс кадры, декодирование и lookahead 2,5 мс.
- Контроллерный стенд: два локальных XInput + два гостевых DS4, независимые
  A/X, смена контроллера внутри трансляции, освобождение обоих виртуальных
  контроллеров после закрытия окна гостя — PASS.
- Пять одновременных трансляций 1080p/60 FPS, удаление зрителей с сохранением
  оставшегося потока и повторное создание лобби — PASS. Это функциональная
  проверка, не длительный замер плавности пяти потоков.
- Туннель loopback: RTT медиана 148,7 мкс, p99 261,0 мкс против прямого UDP
  31,8/67,1 мкс; добавка в одну сторону по медиане около 58 мкс.
  При 100/300/500 Мбит/с в коротком локальном тесте доставлено 100% пакетов.

Исходники измерителей и команды: [scripts/qa](../scripts/qa/README.md).
Сырые локальные наблюдения: [до](qa-1.12.4/baseline.csv),
[после](qa-1.12.4/changed.csv). Исходная рабочая копия, её четыре
незакоммиченных файла и `.qa` оставлены на месте. Правки анализировались
и переносились в отдельный worktree; существующие коммиты/теги сохранены.

## Ограничения

- Нет проверки на двух физических ПК, настоящем Wi-Fi/WAN, в игре,
  с физическими геймпадами, на Windows 10, AMD/Intel GPU или под длительной
  игровой нагрузкой. Parsec установлен, но сопоставимого сеанса на втором ПК
  нет; достоверного сравнения Parsec с DuoLink не выполнено.
  Прямой локальный Sunshine/Moonlight запускался, но пиксельный стенд не дал
  валидных наблюдений; этот неудачный прогон исключён из численного сравнения.
- Снижение скорости уже после подключения не вызывает динамической
  перенастройки Moonlight. Оценка канала при подключении не гарантирует
  отсутствие очередей при посторонних загрузках.
- Старый клиент не сообщает выбранный битрейт: учитывается оценка 15 Мбит/с.
  Его ручной запрос может быть выше. Для защиты общего аплоада обновите обе
  стороны до 1.12.4. PCM/Opus и значения отсутствующих полей протокола проверены;
  полная матрица исторических бинарных версий не прогонялась.
- Локальная сеть и WAN имеют отдельные бюджеты; общий физический Wi-Fi/NIC
  при одновременном LAN+WAN не измерен. Большое число локальных потоков может
  исчерпать возможности GPU независимо от аплоада.
- Исключение живого голосового чата и слышимость на удалённых колонках не
  проверены: в тесте не было активного голосового приложения.
